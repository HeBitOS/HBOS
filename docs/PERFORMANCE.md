# HBOS 性能工作记录

> 本文记录"性能优化"这件事在 HBOS 里**怎么量、改了什么、为什么不改什么**，
> 以及还没做的高价值项。目的有两个：让结论可复核，让后来者不必重新做一遍
> 分析。配套的代码规范见 [`CODE_STYLE.md`](CODE_STYLE.md)。

## 1. 怎么量

| 目标 | 工具 | 说明 |
|---|---|---|
| 冷启动时间 | `make bench-boot`（`scripts/bench_boot.sh` + `boot_time.py`） | QEMU 冷启动，"固件+引导器"与"内核阶段"分开计时，取中位数 |
| 磁盘命令数 / 逐字节语义 | `tests/host/`（宿主机上编译真实 `fat32.c`/`ext2.c`，块设备换文件替身） | 改动文件系统后比对镜像字节与命令计数 |
| 解压正确性 | `tests/host` 风格的一次性差分（本文件 §4 记录了做法与向量） | 用 Python `zlib` 生成真值，逐字节比对 |
| 端到端功能 | `make smoke`、`make fat32-smoke`、`make nogui-smoke` | 启动、DHCP/ping、FAT32 持久化、no-GUI 清单 |

**启动时间为什么必须拆两段**：串口第一个字节并不等于内核开始执行——UEFI 下
OVMF 自己会往串口写控制台输出（`BdsDxe: ...`）。所以 `boot_time.py` 改用
内核横幅 `===== HBOS ... Starting =====`（`kmain` 的第一行输出）作为"引导器
交给内核"的时刻，否则会把 1.6 秒固件时间算进内核阶段。

## 2. 启动时间：7.1s → 3.0s

实测环境：QEMU 512M，`-cdrom`，宿主为普通 x86_64 开发机。

| 配置 | BIOS ISO 冷启动 | 说明 |
|---|---|---|
| 改动前（GRUB `timeout=5`） | **7.11 s** | 其中 5 s 是纯菜单倒计时 |
| 改动后（`BOOT_MENU_TIMEOUT=1`，默认） | **3.02 s** | 固件+引导器 2.98 s，内核阶段 **0.042 s** |
| `make BOOT_MENU_TIMEOUT=0` | **1.86 s** | 自动化/冒烟测试推荐 |

UEFI ISO：**3.92 s**（OVMF 固件 + Limine 3.66 s，内核阶段 0.26 s）。

改动内容：把开机菜单等待时间变成单一事实源 `BOOT_MENU_TIMEOUT`，同时作用于
GRUB（BIOS ISO 与硬盘镜像的 BIOS 路径）和 Limine（UEFI），生成物按取值命名，
改这个变量会自动重生成配置并重建 ISO/镜像。

**为什么默认是 1 而不是 0**：`timeout=0` 时会直接进内核，菜单唤不回来——
实测用 QEMU `sendkey` 连续按住 Shift 3.5 s，内核仍照常启动（但同一手法发方向
键可以停住 `timeout=1` 的倒计时，说明按键注入本身有效）。也就是说 0 会牺牲
"gfxterm 失败时手动选 text fallback"这条恢复路径。`<1>` 秒既保住菜单可见可
选，又拿回 4 秒。

**剩余的大头（未做，属于可选优化）**：内核镜像 31 MB 的 rodata 里，GUI 字形
图集 20.2 MB、壁纸 5.8 MB、HAX blob 2.9 MB 是主角。实测 2 MB 内核 0.50 s、
31 MB 内核 1.68 s（`timeout=0`），即**每 29 MB 约 1.18 s ≈ 25 MB/s** 的引导器
加载成本。压缩这些 blob（如 4-bit coverage、按行游程、整块 DEFLATE）能再拿回
约 1 秒，但会改 `GFN2` 字形格式，而该格式在 HIVE 子模块里有一份同步副本
（`HIVE/src/graphics/gui_font.c`），需要跨仓同步，风险与收益需要在 HIVE 侧
一起评估。

另有一处内核阶段差异：UEFI 下内核阶段 0.26 s，BIOS 下 0.04 s（同样跑 PNG 自
检与三个 seed）。差额出现在 XHCI 探测与自检之间，未定位；因为只占 3.9 s 中的
0.22 s，暂未追。

## 3. 已实施的算法与常数优化

### 3.1 文件复制：256 B 块 → 64 KiB 块（`src/fs.c: fs_copy_file`）

底层每次 `read`/`write` 的**固定开销**与字节数无关：FAT32 每次写要重解析父
目录路径、重扫目录项、重数簇链；ext2 每次读写要重读磁盘 inode；HBFS 文件长度
每增长一次就同步整张 16 扇区文件表。原来的 256 B 小块把固定开销按每 MiB 放大
4096 倍。现改为 `kmalloc(64 KiB)` 搬运（堆不足时退回栈上 512 B），固定开销摊薄
256 倍；缓冲区**不放栈**（任务栈只有 8 KiB），也**不用静态缓冲**（块设备路径
将来可能引入让出点）。

**验证**：guest 内 `wget` 落盘 42600 字节文本，再 `cp s.txt m.txt`、
`cp m.txt d.txt` 连做两次，`stat d.txt` 仍为 `size: 42600 bytes`。

### 3.2 FAT32 整簇读写合并成一条块命令（`src/fat32.c`）

`fat32_read_cluster` / `fat32_write_cluster` 从"每扇区一次 `block_read_sector`"
（最大 64 条命令/簇）改成一次 `block_read_sectors` / `block_write_sectors`：
AHCI 后端合成单条 DMA、USB 合成单条 SCSI。读的是同一段 LBA、写的是同一批扇区
且顺序不变，磁盘镜像逐字节不变。顺带删掉了因此变成死代码的 `fat32_write_sector`。

### 3.3 INFLATE：字级回指拷贝 + 延迟取模 + 固定霍夫曼表缓存（`src/inflate.c`）

- LZ77 回指拷贝：`distance >= 8` 时源区间整体落在目标区间之前，可整字搬运；
  `distance == 1` 是单字节游程，用广播字一次写 8 字节；`2..7` 仍逐字节以保证
  重叠语义正确。
- 非压缩块整段拷贝改用 `memcpy`（源与目标永不重叠）。
- adler32 改为 zlib 式延迟取模（每 5552 字节一次除法），取代每输出字节两次
  `% 65521`。
- 固定霍夫曼表只构建一次；不再每个 `type==1` 块重建 288+30 项规范表。
- **验证**：宿主机编译真实 `src/inflate.c` + 用 Python `zlib` 生成 56 个向量
  （level 0/1/6/9 × {空、单字节、70000 字节单字节游程、distance 3/5/7/8/9、
  长文本、随机、混合、全零、类 PNG}），输出**逐字节一致**；破坏尾校验和的流
  仍被拒绝。内核侧另由 `[SELFTEST] PNG decode: PASS` 覆盖。

### 3.4 校验和：16 位逐对 → 8 字节字（`src/net.c`）

TCP/UDP/IP 的反码和改为一次加 4 个 16 位 lane，并在累加器过半时折叠，避免
64 位溢出（`2^64 ≡ 1 (mod 65535)`，溢出会等于多加 1）。**验证**：宿主机对新
旧实现比对长度 0..70000、偏移 0..7 的全部组合，结果完全相同（另对 30 万字节
做稀疏抽样）。

### 3.5 E1000 轮询不再每次自旋读 MMIO（`src/net.c`）

`reg_read(E1000_RDT)` 原本在每次自旋都做一次（MMIO 窗口是 `VMM_CD` 映射，
每次都是真实 PCIe/VM-exit 事务），而 RDT 是软件私有寄存器、硬件只读，值恒等于
驱动自己上次写入的值。改为内存镜像 `rx_tail`（初始化与消费时同步更新）。

### 3.6 TCP 接收缓冲改为环形（`src/net.c`）

旧实现每 `recv` 一次就把剩余字节 `memmove` 到缓冲头部：消费者小块读取时
（mbedtls 先读 5 字节 TLS 记录头、用户态 `recv` 按用户 buffer 长度读），一个
8 KiB 窗口内的搬移量是 O(窗口²/块)。改为环形后入队写
`(rx_head+rx_len)%cap`、出队从 `rx_head` 起，两端最多各两段 `memcpy`，搬移量
变成 O(交付字节数)。可用空间仍是 `cap - rx_len`，ACK/窗口/丢弃策略不变。
**验证**：QEMU 内 `wget` 从宿主 HTTP 服务拉 42600 字节，串口回显与源文件
逐字节一致；与未改动的 `net.c`（`git checkout` 后重建）对照，同一测试结果相同。

### 3.7 其它

- IPv6 等待循环补 `task_yield()`（`src/net6.c`）：原来 `connect/send/recv` 的
  等待会把一个核占满整个超时窗口，GUI/Shell 无法推进；IPv4 路径本来就是这么
  做的。
- HTTPS 连接顺序：先认字面量 IPv4/IPv6，再 AAAA，最后 A（`src/secure_https.c`）。
  旧顺序对字面量地址也先发 AAAA，在没有 IPv6 解析器的网络里要白白重试
  3×1000 ms。
- 去掉 DHCP 等待循环里重复的 `net_udp_drain()`（该函数一次就排空整条队列）。
- `kcalloc`/`krealloc` 改用字级 `memset`/`memcpy`（`src/core/heap.c`）。

### 3.8 DEFLATE 解压：字级位缓冲 + 9 位一级快表（`src/inflate.c`）

**测量方法**（可复现）：`make inflate-bench`。真值由宿主 Python `zlib` 压缩
生成（`tests/host/gen_inflate_vectors.py`），内核里的 inflate 解压后**逐字节
比对**，因此这个目标同时是正确性差分与吞吐量基准。三档向量都是动态霍夫曼
块（4 KiB / 256 KiB / 4 MiB 原始数据，压缩率 29%~34%），不是 stored block
——纯随机会退化成 stored，测不到霍夫曼路径。

| 向量 | 改动前 | 改动后 | 提升 |
|---|---:|---:|---:|
| 4 KiB（200 次） | 169 MB/s | 218 MB/s | +29% |
| 256 KiB（8 次） | 169 MB/s | 294 MB/s | +74% |
| 4 MiB（1 次） | 171 MB/s | 276 MB/s | +61% |

（宿主为普通 x86_64 开发机，`gcc -O2`，单次运行；量级与相对关系稳定，
绝对值会随机器浮动。）

**改了什么**

1. **位读取器改为批量装填**（`br_fill()` / `br_init()`）。旧 `br_getbits(n)`
   就是 n 次 `br_getbit()` 循环，每次都要判断缓冲是否为空、可能再装一个字节；
   霍夫曼解码每个符号要调用 9~15 次。现在用 64 位缓冲一次装 4 字节，且只在
   剩余不足 32 位时才补充，取 1..15 位都是一次移位 + 掩码。
2. **霍夫曼解码加 9 位一级快表**（`huff_t::fast_sym/fast_len`）。DEFLATE 里
   绝大多数符号码长 ≤ 9，用位缓冲低 9 位（按 MSB-first 语义做位反转后）直接
   索引即可一次命中，省掉逐级比较的循环；码长 > 9 的（主要是距离表的大距离码）
   才回退到逐级比较。
3. 去掉两套位反转实现，统一为可推导的 `br_reverse_bits(v, n)`。

**踩到的三个坑（都靠差分测试逮住，记录以免后人重复）**

- 位缓冲补充循环的条件写成 `bitcnt <= 24` 时，补一次到 32 位后仍会再进一次
  循环，`bitbuf |= w << 32` 把有效位挤出 64 位缓冲；必须是 `< 32`。
- 规范霍夫曼的 `code` 在解码器里是 **MSB-first**（第一个读到的位是最高位），
  而位缓冲是 LSB-first，批量取出的位**必须先按位反转**才能与 `counts`/`first`
  的递推对齐。等价性用"逐位参考实现 vs 批量实现、穷举所有起始位"在宿主侧
  验证过。
- 手写"9 位专用"反转时掩码宽度写错（第 3 轮用了 4 位掩码却按 9 位取高位），
  所有向量立刻失败。位运算要用可推导的通用形式，不靠逐例调参。

**语义不变**：解码出的符号序列、输出字节、adler32 校验结果与改动前逐字节
相同（差分测试保证）；非压缩块跳字节边界时新增"把位缓冲里多装的整字节退回
`pos`"这一步，否则块头会被读错。

### 3.9 ext2 间接块缓存（3 槽）—— 同时消除 12 KiB 栈占用（`src/ext2.c`）

**问题 1（I/O）**：`ext2_inode_block()` 每次调用都要把所在的间接块从磁盘读回来。
顺序读大文件时同一个间接块被连续成百上千次重复读取（一级路径下 1024 个块共享
同一张表）。

**问题 2（栈安全）**：旧实现按路径在**栈上**放 1~3 个 4 KiB 缓冲
（`ind_buf`/`dind_buf`/`tind_buf`），三级路径合计 12 KiB，而任务栈
（`TASK_STACK_SIZE`）只有 8 KiB —— 这是随时会踩爆栈的隐患，也违反
CODE_STYLE §4 "不要在栈上放 >4 KiB 的缓冲"。

**改法**：把三张表移到文件级静态区，并给每个"层级深度"一个独立槽位
（一级用 slot 0；二级 slot 0=顶级表、slot 1=二级表；三级依次向下），
多级路径因此**不会互相驱逐**。顺序读时各槽键几乎不变，命中率接近 100%；
栈占用从 12 KiB 降到 0。

**量化证据**（可复现：`make ext2-diff`）。测试用 mkfs.ext2 + debugfs 造真实
镜像、覆盖 1 B / 511 B / 1 KiB / 4 KiB / 6000 B / 70000 B（跨一级间接边界）
六种尺寸，在宿主机上把块设备换成文件替身并统计底层命令数：

| 指标 | 改动前 | 改动后 | 变化 |
|---|---:|---:|---:|
| 块读命令数 | 214 | 158 | **−26%** |
| 读扇区数 | 427 | 315 | **−26%** |
| 写命令/扇区 | 27 / 45 | 27 / 45 | 不变 |

读回内容与生成规则逐字节一致（差分断言 `failures=0`），分配器语义
（最小空闲块、free 后可复用）不变。

### 3.10 Poly1305：一次越界读修复，以及一次**被否决**的"优化"（`src/crypto/chacha20_poly1305.c`）

新增 `make crypto-test`：用 RFC 8439 官方测试向量（§2.4.2 ChaCha20 分组函数、
§2.5.2 Poly1305 MAC、§2.8.2 AEAD 加解密）做回归，真值来自规范而非本仓库实现。
此前 `poly1305` 路径没有任何独立验证——TLS 里跑通不等于逐位正确。

**修掉一处真实的越界读**：`poly1305_block()` 用 17 字节缓冲（前 16 字节数据 +
第 17 字节的隐含高位 1），但 `load26(block + 12, 8)` 要读 `[12,20)` 共 8 字节，
越过缓冲尾部 3 字节。结果靠 `& 0x3ffffff` 掩码侥幸正确，但属未定义行为
（栈保护/`-fsanitize=address` 下会直接报错）。缓冲扩到 20 字节即可，
`poly1305_mac()` 的内联循环同理。

**被否决的优化（记下来避免后人重做）**：把 `load26()` 的"8 次逐字节载入"
改成"一次 64 位非对齐载入"。这看起来是明显的收益（每个 16 字节块从 40 次
字节载入降到 5 次），实测**反而慢 21%**（484 → 384 MB/s）：

- 原因：`load26()` 读的是刚刚由 `memcpy` 写过的栈缓冲，8 字节载入与 4 字节
  存储**部分重叠**，触发 x86 store-to-load forwarding 失败，每次要等存储提交
  （约十几周期），比逐字节载入的代价更高。
- 结论：这类"减少指令数"的改动在数据依赖紧密的路径上不一定是净收益，
  必须实测。**当前实现保持逐字节载入**。
- 顺带验证：满块（`len == 16`）跳过 `memset` 同样没有可测量的收益
  （在噪声范围内），且我第一版还因此写错了隐藏位的位置导致向量失败；
  现已回退，只保留纯粹正确性相关的改动。真正的提速方向是"一次处理多个块、
  让乘加链流水起来"，属于更大改动，留作后续。

**结论**：本轮对 crypto 只做正确性修复，性能数字与改动前持平
（poly1305 约 550 MB/s、chacha20 约 450 MB/s，宿主 `gcc -O2`）。

### 3.11 HBFS 读写：整段合并成一条块命令（`src/fs.c`）

**问题**：`hbfs_read_data()`/`hbfs_write_data()` 原来**每个扇区**都调一次
`block_read_sector()`/`block_write_sector()`。后端（AHCI/USB）会把连续的单扇区
请求合成一条命令，但每次调用仍要走一遍 LBA 换算与后端派发，跨后端的合并窗口
也有限；CODE_STYLE §5 明确要求"连续扇区用批量接口"。

**改法**：首尾**不完整**扇区仍走单扇区接口（首部需读改写、尾部不足一扇区），
中间**整段**扇区一次 `block_read_sectors()`/`block_write_sectors()` 下发。
可以用批量接口的前提是 hbfs 文件在盘上连续（`hbfs_file_lba()` 由 `disk_slot`
线性推得），任意 `[start, start+n)` 都是连续 LBA 区间。

**量化证据**（可复现：`make hbfs-batch-test`）。该测试把新旧两版算法各实现
一份，跑 9 种 offset × 10 种 count = **90 个边界用例**，断言"两版写出的磁盘
字节逐字节一致、读出的数据逐字节一致"，同时统计命令数：

| 场景 | 旧（逐扇区） | 新（整段合并） |
|---|---:|---:|
| 16 KiB 整段写 | 32 条 | **1 条** |
| 16 KiB 整段读 | 32 条 | **1 条** |
| 90 个用例累计 | 650 条 | 161 条（**−75%**）|

语义不变有两条独立证据：宿主机差分逐字节一致；QEMU 全链路回归
（BIOS+UEFI 启动、三个 seed 写入 tcc headers / hpt repo / web vendor ——
这些是兆字节级写入，走的正是这条批量路径）、`make smoke`、`make fat32-smoke`
全部 PASS。

## 4. 刻意不改的东西（附理由）

1. **FAT32 簇分配游标（把 O(M²) 的 FAT 扫描降为 O(M)）**：会让"总是挑最小编号
   空闲簇"变成"从上次位置继续挑"，从而改变**分配顺序**。仓库里正在维护
   `tests/host/test_fat32_diff.c`（把新旧实现的镜像逐字节比对），分配顺序变化
   会让这类差分失去意义；收益只是每分配一个簇少读几个 FAT 扇区（扇区级扫描
   已经把 128 项合并到一次读）。若要做，应同时更新差分测试并明确接受顺序变化。
2. **内核堆加 next-fit 游标**：2 MiB 池子里，next-fit 更容易让一个小分配吃掉
   一块大空闲区，导致后续大分配失败。当前用"多几次指针追链"换"内存利用率可
   预期"；链表长度上界是"同时在用的分配数"而非分配次数（空闲块就地合并），
   所以扫描不会随分配次数无限增长。取舍写在 `src/core/heap.c` 文件头。
3. **压缩 GUI 字形/壁纸 blob**：见 §2 末尾，需要与 HIVE 子模块同步格式。
4. **`vfs_readdir_at` 每次从 0 重走**：确实是 O(n²)，但 n 受 `MAX_FILES=128`
   限制，绝对开销约 8k 次比较，收益低于改动风险。

## 6. 顺带发现的正确性缺陷（TCP 截断与 FAT32 长名已修复，见 §6.2；引导类未修）

**IPv4 TCP 大响应会在约 113 KB 处截断。** 复现：宿主起
`python3 -m http.server`，guest 内 `wget -O - http://10.0.2.2:8099/t.txt`
（t.txt = 142000 字节文本），串口回显在字节 113742 处中断（行 `01602` 中间），
`wget` 不报错。42.6 KB 的响应完整且逐字节一致，可用来确认修复效果。
（**已定位，见 §6.1**：直接原因是 `net_tcp_exchange` 的固定 80 次迭代上限，
截断点为正文 113760 字节；窗口/ACK 类缺陷是真实但本次未触发的潜在问题。
§6 原记的"已用 `git checkout -- src/net.c` 对照"**方法无效**——环形缓冲已在
HEAD 中，该命令得到同一文件；有效对照见 §6.1.6。）

### 6.1 根因确认（QEMU 实测 + 源码对照，2026-10-01）

**证据等级：A（真机式实测）**——QEMU 11.1.1 + e1000 + `-netdev user`，宿主
`python3 -m http.server`，guest 内核 shell `wget -O -`；同时用
`-object filter-dump` 抓取 net0 全流量做报文级对照。所有结论都有"交付字节数
+ 线序 pcap"两份独立证据，且三次独立运行结果逐字节一致。

#### 6.1.1 结论先行：本次截断的直接原因**不是**环形缓冲，也不是窗口/ACK

**直接原因：`src/net.c:2796` `net_tcp_exchange` 的固定 80 次迭代上限。**

```c
2795:    uint32_t total = 0;
2796:    for (int i = 0; i < 80 && total + 1 < response_cap; i++) {
2798:        if (net_tcp_recv(&conn, response + total, response_cap - total - 1, &got, 4) < 0) break;
```

`net_tcp_recv` 每轮至少消费**一个**已缓冲的 TCP 数据段（见 6.1.4 的机理），
所以整个传输被硬性截断在**恰好 80 个服务端数据段**。142000 字节的响应在
1440 字节 MSS 下需要 100 段（190 字节 HTTP 头单独一段 + 99 段正文），
80 段只够 190 + 79×1440 = **113950 流字节** → 正文 **113760** 字节。
`response_cap`（wget 用 196608，`src/tools/net.c:621`）不是限制因素。

**判定实验（决定性）**——只改文件大小/分段大小，其余不变：

| 用例 | 服务端数据段数 | guest 消费段数 | 交付正文字节 | 结果 |
|---|---|---|---|---|
| 42600 B（42.6 KB 对照组） | 31 | **31** | 42600 / 42600 | **完整，逐字节一致** |
| 100000 B | 71 | **71** | 100000 / 100000 | **完整，逐字节一致** |
| 113760 B（正好 80 段） | 80 | **80** | 113760 / 113760 | **完整** |
| 115200 B（81 段） | 81 | **80** | 113761 / 115200 | 截断 |
| 120000 B | 83 | **80** | 113761 / 120000 | 截断 |
| 142000 B（报告用例） | 83 | **80** | 113761 / 142000 | 截断 |

**"消费段数恒为 80"与分段大小无关**（服务端按 300/600/900/1440 字节切分，
交付字节分别 115011/114361/113221，段数一律 80）。若截断由固定字节预算或
环形缓冲溢出造成，交付字节数应固定而段数应变化；实测恰好相反 ⇒ 这是
**迭代次数上限**，不是容量上限。

#### 6.1.2 与 §6 记录数值的对账（113742 vs 113760）

实测交付正文 = **113761 字节**（三次运行：113761 / 113761 / 113761），
与真值 142000 的公共前缀 = 113760 字节，**无内部空洞、无乱序、无字节损坏**。

§6 的 113742 = 1602 × 71，即 71 字节/行文件里**行 `01602` 的起始偏移**。
把 t.txt 换成 71 字节/行的等价文件复现，截断正好落在**行 01602 内第 19 字节**
——与 §6"行 `01602` 中间"完全吻合。故 113742 是"中断处所在行的行首"，
精确切点是 113760（正文交付 113761，末字节后附换行）。**§6 的"字节 113742"
应订正为 113760。**

#### 6.1.3 报文化证据：不是丢包，是本端主动停读

pcap 报文级事实（截断用例）：

- 服务端→guest 数据段**序列号零空洞**（0 gaps），即对端把数据**发全了**，
  不是"对端停发"。
- guest 每个 ACK 都通告 `win=4096`（常量，见 6.1.5②）；guest 最大 ACK
  相对流偏移 = **113950** = 190 + 79×1440，即只确认了 80 段。
- guest 随后主动发 FIN（`flags=AF`）**放弃**剩余数据；服务端仍在重传第 81 段
  （t=2.4/5.4/11.3/23.3/35.3/47.3/59.3/71.3/83.3 s，指数退避），直到测试进程
  被杀。**"本端丢弃"**：数据到了 guest 的网卡/协议栈，但应用层循环先结束。

#### 6.1.4 为什么"每轮只消费一段"

`e1000_poll` 在回调认领一个包后立即返回（`src/net.c:589` `if (ret) return ret;`），
而 `tcp_dispatch_cb` 对数据段返回 1、对纯 ACK 返回 0。于是
`net_tcp_recv` 内层 `net_poll(..., 80000)` 每次只吃进**一个**数据段就返回；
`net_tcp_recv` 拿到数据后 `break`，外层再 `tcp_conn_read` 一次性取空整个环
（`cap` 极大，见 2798 实参）。故 **1 次外层迭代 = 1 个数据段**，
80 次迭代 = 80 段。

#### 6.1.5 四个嫌疑点逐条裁定（源码行号 + 是否触发）

| # | 位置 | 结论 | 是否本次触发 |
|---|---|---|---|
| ① | `src/net.c:2405-2413` | **成立（结构性缺陷）**：2406 `tcp_conn_append` 返回实际收下字节数却被忽略，2407 `c->ack += dlen` 用**原始 dlen** 无条件推进 ⇒ 缓冲满时 ACK 越过被丢弃字节 | **未触发** |
| ② | `src/net.c:2354` | **成立**：`tcp->win = htons(4096)` 硬编码，与 `NET_TCP_RXBUF_SIZE`（8192，`src/net.h:13`）和真实空闲量 `8192 - rx_len` 完全脱钩 | 持续生效（但见下） |
| ③ | `src/net.c:2419` | **成立（结构性缺陷）**：`c->ack = seq + 1` 无条件跳过缺口并置 `fin=1` ⇒ 上层 recv 返回 0 当 EOF | **未触发** |
| ④ | `src/net.c:3025-3034`（`TCP_PENDING_STAGE_CAP` 见 2928） | **成立（同型缺陷）**：3027-3032 把 `copy` 夹到剩余空间，3033 `p->peer_seq += dlen` 仍按**原始 dlen** 推进 ⇒ 握手期丢数被 ACK 掩盖 | **未触发** |
| ⑤ | `src/net.c:2273-2301`（环形 append/read） | **语义正确**（勿动） | — |

**①未触发的证据**：实测 guest 在途未确认字节峰值 = **4096**（= 通告窗口），
远小于环容量 8192；每轮 `tcp_conn_read` 都把环取空（`rx_len` 回 0），
环从未接近满。故 2406 的截断分支没走到，ACK 推进与实际缓冲字节**一致**
（最大 ACK 113950 = 已交付 113760 + 190 头）。**它是真实的潜在缺陷，
但在当前窗口配置下被②掩盖。**

**②的实际效果（双向危害）**：所有 84 个 guest ACK 一律通告 4096，恒定不变。
(a) 环有 8192 空闲却只报 4096 ⇒ 吞吐被砍半；(b) 环满时**不会**收缩到 0，
即完全丧失流控语义；(c) 由于窗口只有 4096，在途数据永远填不满 8192 的环
——**②恰好把①锁死在"不可达"状态**，这也是①本次未触发的原因。

**③的实际效果**：对端 FIN 与数据缺口同时出现时，`ack` 被直接改写为 `seq+1`
（跳过缺口），`fin=1` 让 `net_tcp_recv`（2658）置 `open=false` 并返回 `*len=0`；
上层 `while (recv(...) > 0)` 自然退出、**不报错**——这是"静默"的通用机制。
但本次截断中服务端**始终没有发 FIN**（它还在重传第 81 段），所以③没有触发。
本次的"静默"另有出处：`net_tcp_exchange` 只在 `total == 0` 时报错
（2803-2808），`total = 113761 > 0` 时**返回成功**，而 `cmd_wget`
（`src/tools/net.c:623`）只检查 `http_fetch < 0`，也不校验 Content-Length
⇒ 部分正文被当成功打印。**③是真实缺陷，但不是本次静默的原因。**

**④的实际效果**：握手期（`established` 后）捎带数据超过 2048 字节时，超出
部分被丢但 `peer_seq` 照推 ⇒ ACK 越过丢失数据，与①同型。本次 GET 请求仅
210 字节（pcap 实测首段 `len=210`），远小于 2048 ⇒ 未触发。

**⑤正确性验证（独立宿主差分测试）**：把 2273-2301 两个函数逐字复制到
宿主测试（**不改 src/net.c**），与"线性队列 + memmove"参考模型做随机差分：
100008 次出队操作、**0 处不一致**；另覆盖空缓冲、零长度、精确填满、
满时追加返回 0、跨环回绕大块读，全部通过。

**42.6 KB 对照组为何逐字节一致**：31 段 ≤ 80 次迭代上限，循环自然跑完；
每轮取空环，`rx_len` 回 0，容量 8192 ≫ 在途 4096 ⇒ ①④永不触发，环的
FIFO 语义与线性实现等价 ⇒ 42600/42600 字节完全一致。

#### 6.1.7 修复必须满足的语义约束清单（逐条可验证）

**A. 传输完整性（直接修复本缺陷，缺一不可）**

1. **去掉/放宽固定迭代上限**：`src/net.c:2796` 的 `i < 80` 不得作为
   "总传输量"预算。循环终止条件必须只由**协议事件**决定
   （收到 FIN 且缓冲排空 / RST / 超时）。验证：142000 字节用例交付
   142000 字节且与宿主文件逐字节一致。
2. **完成判据必须基于字节数而非"有进展"**：`net_tcp_exchange` 若已知
   `Content-Length` 应校验收满；至少不得在"未收到 FIN、缓冲非空、连接
   仍 open"时返回成功。验证：对任意 N ∈ {42600, 100000, 142000, 200000}
   交付 == N，且 wget 无 "--- End ---" 前缺字节。

**B. 流控语义（防回归，②①④）**

3. **真实窗口通告**：窗口 = 环真实空闲量（`NET_TCP_RXBUF_SIZE - rx_len`），
   满时为 0。`src/net.c:2354` 的常量 4096 必须改为按连接计算。
   验证：pcap 中 ACK 的 win 随 `rx_len` 变化；环满时出现 win=0 通告。
4. **ACK 只确认已缓冲字节**：`tcp_conn_append` 的返回值必须被使用，
   `c->ack += 实际收下字节数`（`src/net.c:2406-2407`）。验证：构造
   "单段 > 剩余空间"用例，ACK 不得越过被丢弃字节（可加自检/断言）。
5. **recv 后补窗口更新 ACK**：应用取走数据使窗口重新张开时，必须发送
   窗口更新（或确认 ACK），否则对端在 win=0 后永久停发。
   `tcp_drain_acks`/`net_tcp_recv` 需覆盖该路径。验证：win=0 → 应用 recv
   → 对端恢复发送，传输完成。
6. **FIN 前数据缺口处理**：`src/net.c:2419` 收到 FIN 时若 `seq != c->ack`，
   必须补齐/拒绝缺口，不得直接 `c->ack = seq + 1` 把丢数伪装成 EOF。
   验证：人为丢弃一段后对端 FIN，上层应报错而非静默短读。
7. **rx_stage 同型修复**：`src/net.c:3033` `p->peer_seq += dlen` 必须改为
   `+= 实际拷贝字节数`；容量不足时不得推进。验证：握手期注入 >2048 字节，
   序列号不跳变。

**C. 回归测试与对照**

8. **端到端回归 `tcp-bulk-test`**：≥142000 字节 + 42.6 KB 对照组，
   两者都要**逐字节**比对（不是只看长度），覆盖 80 段边界两侧
   （113760 / 115200）与分段大小无关性（300/600/900/1440）。
9. **既有行为不得回退**：42.6 KB 对照组、`make smoke` 网络项
   （rtl8139/e1000/virtio DHCP + ping）保持通过。

#   shell 内： t  →  dhcp  →  wget -O - http://10.0.2.2:8099/t.txt

### §6.3 FAT32 长文件名静默截断 —— 已修复

**症状**：`writefile persist_test.txt HELLO` 后重启，按原名读不到（看似"文件
消失"）。实测 `persist_ txt`（8.3 截断），而 `cat persist_.txt` 能读出内容
——文件从未丢失，是**名字**丢了。

根因两处：
1. **写路径从不生成 LFN 目录项**（`src/fat32.c`）：只写 8.3 短名，超长名字
   静默截断。读路径本有 LFN 解析，但写侧从不产生，永远读不回原名。
2. **重启装载时根目录名边界算错**（`src/fs.c` `fat32_rebuild_dir`）：
   `plen + 1 + nlen >= MAX_FILENAME` 对根目录（无分隔符）多算 1 字符，把
   名字正好 31 字符（`MAX_FILENAME-1`）的文件整条跳过、不进扁平表。

修复：补规范 LFN 条目序列（校验和基于最终短名、>13 字符多槽、目录内唯一
8.3 短名带 `~N` 尾），并修正根目录前缀长度计算。

**实测**：12/13/14/25/26/27/31 字符文件名写入 → 重启回读 **7/7 逐字节通过**；
宿主 `mdir` 可见原名；`make fat32-smoke` 继续 PASS。

> 原 `make fat32-smoke` 长期未发现该缺陷，因其测试文件名全为 8.3 兼容
> （`persist.txt`/`testdir`/`nested.txt`）——**测试盲区**，长名用例已补。

## 8. 顺带发现的引导缺陷（未修，已定量定位，待立项）

**低内存机器上 GRUB 无法加载内核：`grub_relocator_alloc_chunk_addr: out of memory`。**

复现（QEMU，同一 `build/hbos-bios.iso`，实测）：

| `-m` | 结果 |
|---|---|
| 512M / 256M | 正常启动到 Shell |
| 128M / 96M / 64M | 卡住，VGA 屏显示 `error: lib/relocator.c:grub_relocator_alloc_chunk_addr:1300:out of memory.`（串口无输出——GRUB 走 VGA，不是内核输出） |

VirtualBox 默认内存档位（128M/256M）落在故障区间，故真机/VBox 上更易命中。

**根因**：`linker_bios.ld` 把内核定在固定物理地址 `16M`，GRUB 重定位器必须找到
**一整块连续**物理内存容纳全部 LOAD 段。当前内核物理足迹：

```
.text    16MiB .. 17MiB
.rodata  17MiB .. 46MiB    ← 29 MiB，其中内嵌 GUI 字体 gui_font.bin 占 20 MiB
.bss     46MiB .. 91MiB    ← 45 MiB，几乎全是静态数组
合计     16MiB .. 91.1MiB（约 75 MiB 连续）
```

`.bss` 是 `NOBITS`（文件里不占空间），但 Multiboot2 加载语义要求 GRUB 按 `MemSiz`
预留，这 45 MiB 全落在 GRUB 的账上。45 MiB 的构成：

| 符号 | 位置 | 大小 |
|---|---|---|
| `ramfs_storage[MAX_FILES][RAMFS_MAX_FILE_SIZE]` | `src/fs.c:59` | 16.00 MiB |
| `g_back_buffer`（1920×1080 帧缓冲） | `src/graphics/graphics.c:43` | 7.91 MiB |
| `g_playwav_buf` | `src/tools/audio.c:34` | 5.00 MiB |
| `task_fd_tables` | `src/core/` | 2.38 MiB |
| `heap_pool` | `src/core/heap.c` | 2.00 MiB |
| 其余（PNG/JPEG/BMP 解码平面等） | — | ~5.9 MiB |

**候选修法**（互不冲突，建议按序）：

1. **把大静态数组改为启动后动态分配**（收益最大，75 MiB → ~30 MiB）：
   `ramfs_storage`、`g_back_buffer`、`g_playwav_buf` 从 `.bss` 移出，内核起来后
   从物理页/堆分配。这不改 Multiboot2 语义，只是别让 GRUB 替内核预留。
2. **调整加载地址**：`16M` 在低内存机器上偏高（固件/EBDA 占用低位），可评估
   更低或更合适的固定基址；或改用 PIE/可重定位加载让 GRUB 自行选点。
3. **引导前内存检查 + 明确提示**：GRUB 配置里探测内存，不足时提示
   "HBOS 需要 ≥256MB 内存"，而不是抛出 GRUB 内部错误——用户至少知道该改什么。

参考对照：`build-nogui/`（`HBOS_ENABLE_GUI=0 HBOS_BUNDLE_APPS=0`）的内核
仅 2.16 MiB、`.bss` 段 0x28e9b20（约 41 MiB），说明 20 MiB GUI 字体与解码平面
是 `.rodata` 侧的主要增量。

### 8.1 VirtualBox Guru Meditation 实证（已定位，`src/boot.asm` 已修）

> **修订说明（2026-10-01）**：本节初版曾把崩溃 EIP 判读为 `app_diag_draw`
> 并推论"GRUB 重定位失败导致内核镜像不完整"。该判读**有误**：初版误用**当前
> 内核**的符号表去解析**旧 ISO**（9/30）的地址。用正确的旧内核符号表解析后，
> `0x010a3850` 对应 `long_mode+0xb`，真实根因如下所述，与 §8 的 GRUB 低内存
> OOM **不是**同一因果链。初版结论已作废。

用户提供 4 份 `VBox.log`（VirtualBox 7.2.20 r175154，宿主 Arch Linux 7.2.7）。
崩溃的共同特征是 **VCPU0 三重故障**，两份崩溃日志 RIP 完全一致（确定性复现）：

| 日志 | 结果 |
|---|---|
| `VBox.log` | `VINF_EM_TRIPLE_FAULT`，`eip=010a3850` |
| `VBox.log.1` | `VINF_EM_TRIPLE_FAULT`，`eip=010a3850` |
| `VBox.log.2` / `.3` | 未进内核，干净退出 |

**决定性证据是 VMX exit history**（比崩溃后的寄存器 dump 可靠——日志明写
`Skipping ring-0 registers`，`cr0=0x11/cr3=0/EFER=0` 是故障后 CPU **复位态**，
不是故障现场）：

```
Exit No.:  RIP                Exit
1583866:   0x10a377e          cpuid        (eax=0x80000000)
1583867:   0x10a3790          cpuid        (eax=0x80000001)  ← 检测 long mode
1583868:   0x10a3843          out %ax,(%dx)                     ← 落入 .no_long
1583869:   0x10a3850          VMX_EXIT_TRIPLE_FAULT
```

旧内核符号表（`nm` 解析 9/30 的 `hbos.bin`）：

```
0x10a383b  _start.no_long   → MOV AX,2001H; MOV DX,1004H; OUT DX,AX
0x10a3845  long_mode
0x10a3850  long_mode+0xb    → mov %ax,%ss        ← 三重故障点
```

**根因**：`src/boot.asm` 的 `.no_long` 分支写完 QEMU 专用的 debug-exit 端口
`0x1004` 后**没有 halt / 没有跳转，直接贯穿（fall through）**进紧邻的
`long_mode`（64 位代码）。于是在"不支持长模式"的机器上：32 位保护模式下执行
`mov %ax,%ss`（空选择子）→ #GP → 无 IDT → #DF → **三重故障**。
VBox 的 `0x1004` 端口无特殊语义（该端口是 QEMU 的 `isa-debug-exit`），所以
"关机"没发生，反而贯穿了。

**修复**（已由用户完成，`src/boot.asm:149-151`）：在 `.no_long` 末尾加
`hlt` + `jmp $`，截断 fall-through。修复后行为从"静默三重故障"变为
"干净停在 hlt"，不再出现 Guru Meditation。

**VBox 侧还需一个配置修正**（与本缺陷独立、但决定能否真正启动）：
即便 ostype 改为 `Other_64`，若 VM 的 `longmode`/`pae` 仍停留在 32 位时代的
`off`，VBox 会向 guest 屏蔽 CPUID `0x80000001.EDX` 的 **LM(bit29)**，HBOS
据此正确判定"不支持长模式"→ 走 `.no_long` → 停在 `hlt`（黑屏、不崩溃）。
实测修复前后（`hbos-disk`，BIOS，512 MB）：

```
修复前: EnablePAE=0, LM - AMD64 Long Mode = 0 (1)
        Gst 80000001 EDX = 0x08000800  → LM(bit29)=0  → 停在 hlt
修复后: --pae on --longmode on
        CPUM: SetGuestCpuIdFeature: Enabled LONG MODE
        PAE=1(1)、LM=1(1)
        Gst 80000001 EDX = 0x28100800  → LM(bit29)=1  → 正常进 long mode
```
修复后 VBox 上 HBOS 完整启动至模式选择界面（自检 `PNG decode` /
`Linux event/AF_UNIX` / `POSIX/ramfs` 全 PASS，EHCI ready）。

**与 §8 的区别**：§8 是**低内存下 GRUB 重定位 OOM**（真实且独立，QEMU 实测
128 M 起不来、no-GUI 版 96 M 能起），优先级与修法仍按 §8 所述；本节是
**内核引导代码缺陷 + VBox CPU 特性配置**，两者无因果关系。初版把二者强行
关联的推论已作废。
