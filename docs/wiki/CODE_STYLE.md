# HBOS 代码规范与注释规范

> 适用范围：`src/`（内核、驱动、文件系统、GUI、工具）、`scripts/`、`tests/`。
> 这份文档把仓库里已经形成的约定写下来，供新代码和改动对齐；它不引入新的
> 风格流派，只是把"读起来像 HBOS"这件事变成可检查的条目。

## 1. 语言与工具链

- 内核与驱动：**C99**，freestanding（`-ffreestanding -mcmodel=kernel`），
  不使用 libc、不使用 `malloc`（用 `kmalloc`/`kfree`）。
- 内核**禁用** x87/MMX/SSE：`-mno-80387 -mno-mmx -mno-sse -mno-sse2`。
  原因：中断/异常路径不保存向量寄存器状态。因此**不要**写浮点、`__m128`、
  自动向量化的代码；需要提速就用 8 字节整数（`uint64_t`）字级实现。
- 内联汇编统一 `__asm__ volatile` + AT&T 语法，端口 I/O 走 `core/io.h`。
- 用户态组件（`.hax`、Linux ABI 兼容层测试）可以用 `USER_CFLAGS` 允许的
  现代特性，但不要反向依赖内核内部头文件。
- 编译必须做到 **零 warning**（`-Wall -Wextra` 已开启）。新增的
  `unused-function` / `unused-parameter` 等要么用掉、要么删掉，不要留死代码。

## 2. 命名

| 对象 | 约定 | 例子 |
|---|---|---|
| 函数、变量、类型 | 小写 + 下划线 | `fat32_read_cluster`、`tcp_conn_t` |
| 导出的类型 | `_t` 结尾 | `gui_font_size_t`、`block_backend_t` |
| 编译期常量 | 全大写宏 | `NET_TCP_RXBUF_SIZE`、`HBFS_TABLE_SECTORS` |
| 文件内静态状态 | `g_` 前缀或 `static` 局部 | `g_fat32_cluster_buf` |
| 布尔语义 | `is_`/`has_`/`need_` + `int`/`bool` | `link_ready`、`need_ack` |
| 结构体字段 | 小写，必要时带单位 | `rx_len`、`timeout_ms`、`deadline_ticks` |

单位一律写进名字（`_ms`、`_px`、`_lba`、`_hz`），不要靠注释或约定记忆。

## 3. 注释

注释解释 **为什么**，代码本身表达 **做什么**。具体要求：

1. **文件头**：每个 `.c` 开头用 `/** @file ... @brief ... */` 说明职责；
   若文件里有非显然的算法/协议/性能取舍，加一段"性能要点/不变式"。
   参考 `src/lib/string.c`、`src/core/heap.c`、`src/inflate.c`。
2. **每个非平凡函数**：说明参数含义、返回值、以及**不变量**（调用前提、
   是否可重入、是否需要持锁、失败时的部分状态）。公共 API 用
   `@param`/`@return`。
3. **复杂算法的推导**：例如字级字符串运算的越界不变式、校验和的模数性质、
   环形缓冲的取模下标——把"为什么这样写是对的"写清楚，而不是复述代码。
4. **反直觉的修复**：把"旧写法为什么慢/为什么错"和触发它的用户可见现象
   写进注释（例：`src/shell/shell.c` 里 PS/2 重复初始化的说明）。这类注释
   防止后人把优化改回去。
5. **不要**写 `i++; // i 自增` 这种复述式注释；也不要用注释保留死代码。
6. 中文为主、术语保留英文（`first-fit`、`MMIO`、`DEFLATE`），中英文之间
   按仓库既有习惯留一个空格。

### 3.1 头文件注释模板（强制）

每个 `.h` 都按下面的块结构写。它存在的意义是让**人**能在打开文件的 10 秒内
判断"这是谁的接口、归哪一层、能不能改"——AI 读得懂的东西，人也必须读得懂。

```c
/**
 * @file    xxx.h
 * @brief   一句话说清这个头文件导出什么能力（≤30 字）
 *
 * @layer   core | fs | net | gui | user | app      ← 归属层
 * @owner   src/core/（实现文件所在目录）
 * @stable  ABI 稳定度：stable / internal / experimental
 *
 * 依赖    本头文件 include 了谁，为什么必须 include 它（而不是前置声明）
 * 被依赖  谁会 include 本文件；新增依赖方必须先确认没跨越层边界
 *
 * 索引头文件（见下：本文件导出清单，名字 + 一句话职责）
 */

#ifndef HBOS_XXX_H
#define HBOS_XXX_H

/* ═══ 数据模型 ═══════════════════════════════════════════════════════
 * 只放类型定义。每个结构体上方写明：
 *   · 生命周期：由谁创建、由谁释放、能不能栈上分配
 *   · 并发语义：是否要求调用方持锁 / 是否只读 / 是否可跨任务共享
 *   · 不变量：字段间的隐含约束（例：len 恒 ≤ cap）
 */

/* ═══ 常量与宏 ═══════════════════════════════════════════════════════
 * 单位写进名字（_MS / _BYTES / _PX / _LBA）。魔数不许裸奔。
 */

/* ═══ 接口 ═══════════════════════════════════════════════════════════
 * 每个函数：@param 写"什么"，@return 写"失败具体返回什么以及为什么",
 * 再补一行 **不变量/前置条件**（持锁？可重入？失败时部分状态如何？）
 */

#endif /* HBOS_XXX_H */
```

三条硬约束，写不出来就说明接口没设计清楚：

1. **`@layer` 必须是唯一值**。一个头文件跨层，就是该拆了。
2. **`@stable` 为 `stable` 时**，改任何函数签名 = 改 ABI，必须同步
   `docs/` 与所有调用方；`internal` 可以在层内自由改；`experimental`
   必须写一句"何时会转正或删除"。
3. **函数注释里的"不变量"不许省**。只写"@param x 输入值"的注释等于没写，
   它没告诉下一个改代码的人哪里会踩雷。

体量参考：单个头文件超过 ~400 行先考虑按能力拆分；`#include` 数量超过
10 个通常说明这一层吸了太多别的东西。

#### 3.1.1 索引头文件（强制）

在 `@stable` 之后、`#ifndef` 之前，写一段**索引**——按"类型 / 宏 / 函数"
三类逐行列出本文件导出的**全部**名字及一句话职责。

```c
 * @stable  stable
 *
 * 依赖    ...
 * 被依赖  ...
 *
 * 索引头文件
 *   类型  gui_service_caps_t      能力与限额，服务端填写
 *         gui_service_create_t    创建窗口的入参
 *   宏    HBOS_GUI_SERVICE_ABI_MAJOR   ABI 主版本，不匹配即拒调
 *   函数  gui_service_window_open     按 owner_task 开窗，返回句柄
 *         gui_service_window_poll     取一个事件，无事件返回 0
 */
```

规则：

- **枚举值不单列**，归到承载它的那一个类型/宏名下（想让人知道有哪些值，
  就在那行职责里点出来，如"…op 取 GUI_SERVICE_V2_*"）。
- **`static inline` 和 `#define` 型"函数"算函数**，写在实际语义那一类。
- 每行职责 ≤ 20 字，写**用途**不写签名（签名就在下面 30 行处）。
- **必须与实际内容一致**。加/删导出而不改索引 = 文档撒谎，比没有索引更坏。
  `make check-headers` 会用脚本对一遍（见 §3.1.2），review 时也要肉眼确认。
- 索引只列**对外可见**的名字；文件内 static、仅本文件 include 的私有头
  不列。
- 头文件很短（< 30 行、导出 < 5 个）时索引可以并入 `@brief` 尾句，但要
  保持"名字 + 职责"的形态，不要退化成散文。

为什么需要它：读代码的人（尤其是 AI）常常只需要"这个头文件能给我什么"，
不该为了找 `pmm_alloc_blocks` 是否在这儿而从第 1 行滚到第 90 行；反向地，
改接口的人一眼就能看见"我要改的名字在索引里，说明它是公开契约"。

#### 3.1.2 自动检查

```sh
make check-headers        # 或 bash scripts/check_headers.sh
```

脚本校验五件事：**缺模板头**（前 40 行没有 `@layer`/`@owner`/`@stable`）、
**缺索引**（有 `@stable` 但没有"索引头文件"段）、**索引对不上**（索引里点名
的标识符在文件正文里不存在）、**索引缺职责**（索引行只有名字没有一句话）、
**`@brief` 计数不符**（`导出 N 个接口（A 类型 / B 宏 / C 函数）` 里的 C 与
实际函数声明数对不上）。

最后一项是重构期的关键保险：改函数时最容易忘的就是同步 `@brief` 那一行，
忘了文档就开始撒谎。数函数声明由 `scripts/count_decls.py` 负责，shell 正则
数不准——`static inline int foo(\n …\n) {` 这种跨行且以 `{` 收尾的声明会被
行尾分号规则整批漏掉（libc 头因此数成 0），而只做括号配平又会把结构体里的
函数指针成员算进去（`xhci.h` 从 13 涨到 18）。这两个坑都钉在那份脚本里。

它**不**检查"是否列全"——那需要完整 C 语法分析，且 §3.1.1 允许短头文件把
索引并进 `@brief`，硬比对必误报。列全与否交给 review。

两级豁免：`third_party/`（上游代码）完全不查；`src/user/libc/` 下的
Linux ABI 兼容头（`ln.h` `wd.h` `init.h` `dlfcn.h` `link.h`）**只查索引
不查模板头**——它们的"层次"由 glibc 兼容性决定，不由我们的分层决定，套
`@layer` 反而误导；但这恰恰是最需要导出清单的一类头文件。

## 4. 结构与错误处理

- 一个函数一个职责；超过 ~80 行的函数先考虑拆出静态辅助函数。
- 栈是稀缺资源：任务是 `TASK_STACK_SIZE`（8 KiB），启动栈 64 KiB。
  **不要**在栈上放 >4 KiB 的缓冲；需要大块缓冲时用 `kmalloc`
  （见 `fs_copy_file`），或用文件内共享静态缓冲并说明"为什么不会并发"
  （见 `src/fat32.c` 顶部）。
- 失败路径必须释放已获取的资源，并且**按获得顺序的逆序**释放；多出口函数
  用单一 `result` 变量 + 末尾统一清理，避免漏 `kfree`。
- 返回值约定沿用各子系统现状：块设备 `0/-1`，文件系统 `>=0` 字节数或 `-1`，
  网络 `0/-1` + `net_last_error()`。修改返回值语义等于改 ABI，必须同步
  调用方与文档。
- 中断上下文禁止调用 `console_print` / `gfx_*` / 可能阻塞的 I/O。

## 5. 性能纪律

1. **先量再改**：启动时间用 `make bench-boot`；网络/文件系统的行为回归用
   `make smoke`、`make fat32-smoke`；改动声称"更快/等价"时给出前后数字或
   逐字节比对结果（见 `docs/wiki/PERFORMANCE.md` 的方法）。
2. **避免逐字节循环**：大缓冲区一律用 `lib/string.c` 的 `memset`/`memcpy`
   或 8 字节字级手写循环。
3. **避免二次方**：在会被高频调用的路径上（每次 `read`/`write`/`recv`/
   `open`）不要重新扫描整个结构；缓存或增量推进（游标），并写清楚缓存的
   失效条件。
4. **批量化设备命令**：连续扇区用 `block_read_sectors`/`block_write_sectors`，
   不要循环调用单扇区版本（AHCI/USB 后端会把它们合成一条命令）。
5. **不要引入无谓的等待**：等待循环必须有截止时间且调用 `task_yield()`
   （协作式调度，不让出就会独占 CPU）。
6. **优化不能改变语义**：除非明确要求，不改磁盘格式、不改线上协议、不改
   结构体公开字段。分配顺序、写盘字节序列这类"看起来无关紧要"的东西，
   可能正被宿主机差分测试逐字节比对（`tests/host/`），改动前先确认。

## 6. 提交与验证

- 改动前先编译：`make -j$(nproc)` 必须无 warning。
- 涉及启动路径的改动跑 `make bench-boot`；涉及文件系统/网络的跑对应冒烟。
- 提交信息建议用 `perf(<子系统>): <做了什么，为什么>` / `fix(...)` /
  `docs(...)` 形式，说明**可复现的证据**（测得的秒数、命令计数、字节比对）。
- 新增脚本、Makefile 目标、公共 API 时同步更新 `README.md` 与本目录文档。
